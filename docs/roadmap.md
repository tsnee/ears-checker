# Roadmap

Planned changes, each its own OpenSpec change. Order and scope can change; the specs under `openspec/specs/` are what's built.

## Next

In this order, grouped by theme. Each theme is one branch and one pull request, merged when the theme is done.

### In order

In this order (set 2026-11-11); their themes are chosen when they're planned.

1. **Markdown tables, read as GitHub reads them** (theme branch `batch-tables`). `read-markdown-tables` (done, archived 2026-11-12, merging with the theme): tables found in a paragraph's raw lines and each cell re-parsed as inline text, matching GitHub's renderer, with a warning for a row whose extra cells GitHub hides. Then its follow-up, `read-table-before-underline` (done, archived 2026-11-13): a `---` or `===` line directly under a table, which the parsers read as a setext heading, read as the table's next line, as GitHub reads it (the owner chose this, 2026-11-12). Then **Markdown read with cmark-gfm on every platform** (next; PR #25 stays open until it's done, the owner chose this 2026-11-13): the batch's security review (2026-11-13) found three ways small crafted input makes `Tables` overflow the stack or take quadratic time, and a probe found that cmark-gfm, GitHub's own parser, matches GitHub on all 144 conformance fixtures where commonmark-java's and micromark's table extensions don't (`docs/measurements/table-parser-probe.jsonl`). A spike compiled cmark-gfm 0.29.0.gfm.13 to WebAssembly with wasi-sdk: on Node and on the JVM (Chicory's build-time compiler, clang `-O2 -fno-inline-functions`, no extra JVM flags), its output matched native cmark-gfm on every fixture (`docs/measurements/cmark-gfm-wasm-spike.jsonl`). On Scala Native it would be compiled into the binary. It replaces the three parsers and the table code (`Tables`, `Rows`, likely `SourceLines`), and with them the security findings; the batch is reviewed again before the merge.
2. **OpenSpec 2.0** (its own theme, next after tables, which now include the cmark-gfm change; the owner chose this, 2026-11-13). The owner's laptop has OpenSpec 2.0.0, released 2026-11-11, while CI pins 1.17.0 (`.github/tools/package.json` and its lockfile). 2.0 keeps the workflows and validation, installs the skills in `.agents/skills/` with links from `.claude/skills/` (`openspec update --dry-run` on 2026-11-13: 11 skills added there, each `.claude/skills/<name>/SKILL.md` replaced by a link), removes the `/opsx:*` commands (unused here), and no longer needs `delivery: skills`. One change, no spec changes, like `update-openspec` (2026-11-11): pin 2.0.0 in CI, commit `openspec update`'s files, add `.agents/` to `.prettierignore`, reword `CLAUDE.md`'s Workflow note on `openspec update`, and check that Claude Code finds the skills through the links.
3. ~~**A list after a link definition, read the same on every platform.**~~ No longer needed: it was commonmark-java's (it started a list on a line such as `2) The calendar shall sync.` after a link reference definition, where GitHub, commonmark.js, and cmark read paragraph text), and read-markdown-with-cmark-gfm reads every platform with cmark-gfm instead (2026-11-14).
4. **The OpenSpec parse error names the file.** "Not OpenSpec change or spec JSON: …" doesn't say which input it's about, so a run over several files leaves the user guessing which one failed (found by the test review, 2026-11-11). Name the input, as the read errors do, with a test and a case in `scripts/cli-cases`.
5. **`--help` anywhere on the command line.** It works only as the first argument: on 2026-11-07, `ears-check --output json --help` printed "Unexpected option: --help" and exited 2, where other programs accept it anywhere (the README documents it as the first argument). A fix in option parsing, with a test per position.
6. **Control characters and lone surrogates in JSON output.** zio-json escapes only the C0 control characters: C1 controls (such as the 8-bit CSI, U+009B), DEL, and U+2028/U+2029 from the input reach `--output json` raw (security review, confirmed with the jar, 2026-11-11). Few terminals act on a UTF-8 C1 control and JSON output is for tools, but escaping them costs a parser nothing (a `\u` escape and the raw character are the same JSON string) and doesn't change the document's version. And an OpenSpec requirement with an escaped lone surrogate (`"\ud83d"`) is written as `?` by the jar and the native binary, and as U+FFFD (`ef bf bd`) by Node (seen 2026-11-08 in the raw output bytes), so the platforms' JSON differs. Escape it as `\uXXXX` on every platform, with a case in `scripts/cli-cases`. OpenSpec's own output can't produce one. Its first test is ready-made: `CheckerSuite`'s "every document is one line…" property with a separator sentence that has a finding (so U+2028 reaches the fix), asserting no raw U+2028 or U+2029 in the JSON; tried on 2026-11-11, it fails today (`Checker.report` writes zio-json's output as it is).
7. **Bidirectional overrides in text output.** escape-text-output escapes control characters and line separators from the input, but not Unicode's bidirectional formatting characters (U+202A to U+202E, U+2066 to U+2069), which aren't control characters: a requirement or file name carrying them can make a finding display in a different order than it's written ("Trojan Source"). Few terminals act on them; editors and web views of saved output do. Escape them in text output and messages as well, with a test and a case in `scripts/cli-cases` (a non-goal of escape-text-output, 2026-11-11).
8. **A size limit on each input**, for untrusted input (SECURITY.md counts it as in scope, with this limit known). Its memory grows with the input, mostly in the Markdown parser (commonmark-java took about 1 GB for a million nested emphasis markers), so a limit on nesting wouldn't help; a limit on bytes would.
9. **Directories as input** (`ears-check docs/`), and **a CI snippet or GitHub Action** for checking requirements in other projects.
10. **A Developer ID–signed, notarized macOS binary**, so macOS opens it however it's downloaded (today it has only the linker's ad-hoc signature, which Gatekeeper rejects: `spctl --assess` on 0.2.0's binary, 2026-11-12); it needs a paid Apple developer account. And **more native platforms**: Windows, and macOS on Intel, which GitHub offers only on its `-intel` and larger runners.
11. **List the Coursier app in Coursier's own channel.** A pull request to `coursier/apps` adding `ears-check` to its contrib channel would make `cs install --contrib ears-check` work without this repository's URL; worth it once people use the app.

### A general Scala.js link checker

12. **A general Scala.js link checker**, extracted from `ears.linkCheck`. It writes a program that references every public operation of a Scala.js library from its SemanticDB, and `scripts/check-scalajs-link` links it against only the published artifact; it caught 0.1.0's `java.util.Locale` bug, which the tests hid (zio-test brings in scala-java-locales). Searches on 2026-11-07 found no existing tool that does this. To be general it needs: the operation shapes it now refuses by name (overloads, `using` parameters, varargs, givens, extension methods, bounded type parameters, constructors that take arguments) or a way to exclude one; a build integration others use (a Mill plugin, and an sbt plugin: GitHub's code search on 2026-11-08 found about 38,800 `build.sbt` files enabling `ScalaJSPlugin`, against about 300 Mill build files using `ScalaJSModule`); a check on Scala 2 libraries' SemanticDB; and its own repository, versions, and documentation. It's already a separate module with no dependency on the classifier, so it can be extracted whenever it's proved itself here.

## Later

- **Watch cmark-gfm**, which is vendored in `ears/markdown/cmark-gfm` and which Dependabot doesn't see (it's in no package registry): its releases (0.29.0.gfm.13, 2023-07-21, was the latest on 2026-11-13) and its security advisories, updating with `scripts/update-cmark-gfm` and rerunning the GitHub probe (`docs/measurements/table-parser-probe.jsonl`) on an update. And the position bugs the reader works around, so it needs no change when they're fixed (the comments that cite them can then name the fixed release): cmark's, which cmark-gfm shares and would have to take up, filed by the owner on 2026-11-13 as commonmark/cmark#660 (a paragraph after a link reference definition starts on the definition's line, as do its inlines; `CmarkLines`) and covered by the open pull request commonmark/cmark#298 (inline lines don't advance after a backslash hard break or a link whose title is on the next line; `CmarkLines`); and cmark-gfm's own around a table that interrupts a paragraph (`CmarkReader`), not yet reported. (commonmark/cmark#659, a setext heading ending a line late, no longer matters: cmark-gfm reads the tables it affected.)
- **Markdown back to its old speed.** With cmark-gfm on every platform, every build reads large Markdown in 1.4 to 1.5 times the time it took before (run `2026-11-14T13:20:19Z` against `2026-11-13T13:41:13Z`, `docs/performance.md`), and the JVM pays more on small files (1.33 s against 0.87 s on 1 MB). Since it's the same on every build, start with a profile of the native binary with full stacks (macOS `sample`) to see whether the time is cmark-gfm's or the shared Scala's (the records, `CmarkTree`, `CmarkReader`); if it's decoding, binary records (fixed-width numbers instead of decimal text) are the next step, which changes the entry point's format and `CmarkTreeSuite`. JFR's default stack depth (64) was too shallow for the JVM's profile; raise it (`jdk.ExecutionSample#stackdepth`) when profiling the jar.
- **Third-party notices for the jar's JVM dependencies** (ZIO, cats, cats-parse, decline, zio-json, Chicory): the jar carries cmark-gfm's notices but not theirs, a gap from before read-markdown-with-cmark-gfm, which added cmark-gfm's.

- **At the 0.3.0 release, npm's follow-ups** (`publish-npm-packages`): set up the stage-only trusted publisher on each npm package within the two days before tagging; after the release, check the shape of `npm stage list --json` against `scripts/approve-npm-release`, and that npm shows provenance for both packages (if not, switch to publishing directly behind an environment approval). Once it does, `docs/release-files.md` and the READMEs can mention npm's provenance.

- **Compile Scala Native in parallel again.** CI, CLAUDE.md, and CONTRIBUTING.md compile the Scala Native modules one at a time because Scala Native 0.5.12's compiler plugin caches its definitions globally with no locking (scala-native#4950). Once a Scala Native release fixes it, raise Scala Native and drop the extra step and the rule.
- **Coverage on Codecov, with a badge.** CI would upload each module's scoverage XML, in a job apart from those that build release files (the uploader is outside code), with a `continuous-integration` requirement. On 2026-11-07, Codecov's API knew the owner's account and listed `ears-checker`, never activated and with no coverage; check its current terms for public repositories (token or tokenless upload) when planning. Coverage minimums are already enforced per module in CI.
- **One predicate for which characters are escaped.** `Visible.escape` (text output and messages) and `Logging.escape` (log lines) each spell out the same predicate: ISO control characters, U+2028, and U+2029. Share it, so the two can't drift apart; no change in behavior (a suggestion from escape-text-output's verification, 2026-11-11). The bidirectional overrides (item 7) would then join both at once.
- **Suppressing findings**, for example `<!-- ears-check: ignore -->` before a sentence, or a file of known exceptions, so a document can waive a finding without rewording.
- **Building the Linux binaries in a container** (such as `debian:bookworm`, glibc 2.36) once GitHub retires `ubuntu-22.04`, the runner that sets their oldest glibc today.
